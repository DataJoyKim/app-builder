# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

App Builder is a Spring Boot service that lets non-developers generate standard CRUD/admin pages through a web console instead of hand-coding them. A "console" UI defines entities, views, workflows, and data sources; the runtime interprets those definitions at request time to serve the actual pages and APIs. Java 17, Spring Boot 3.3.4, Thymeleaf + AdminLTE for the UI, H2 as the embedded application database (with MySQL/MariaDB support for connecting to *target* databases the generated admin pages manage).

## Commands

- Run the app: `./gradlew bootRun` (Windows: `gradlew.bat bootRun`) — serves on port 8080, console at `/console`
- Build: `./gradlew build`
- Run all tests: `./gradlew test`
- Run a single test class: `./gradlew test --tests "com.prometis.appbuilder.workflow.WorkflowServiceTest"`
- Run a single test method: `./gradlew test --tests "com.prometis.appbuilder.workflow.WorkflowServiceTest.methodName"`

Dev settings live in `src/main/resources/application.yml`: `spring.devtools.restart`/`livereload` are on, Thymeleaf/static resource caching is disabled, and `hibernate.ddl-auto: update` auto-migrates the embedded H2 schema at `C:\admin-builder\data\admin-builder` on startup. The H2 console is exposed at `/h2-console`.

## Architecture

### Two layers: the console (design-time) and the runtime (serve-time)

- **Console** (`console/`, templates under `templates/console/**`): a Thymeleaf+AdminLTE SPA-ish UI at `/console/*` where an admin defines entities, views, workflows, data sources, users/authorities, common codes, etc. `ConsoleViewController` is a single generic route (`/console/{path}` → `console/contents/{path}.html`) — most console screens are just static content panels that call the REST endpoints in `console/rest/*RestController` to CRUD the definition tables. `ConsoleSecurityFilter` (registered in `FilterConfig` for `/console/*`) gates the whole console behind authentication + a "console access" authority code.
- **Runtime** (`view/`, `templates/pages/**`, `templates/template/**`): serves the pages an end user actually visits, driven by data saved via the console. `ViewBuilderController`:
  - `GET /` renders `pages/index` (optionally behind auth, per `Layout.useAuthValidation`).
  - `GET /pages/{objectCode}` looks up a `ViewObject` by code and dispatches based on `ObjectType`: `FILE` → `template/mf-template` (a plain custom HTML/JS page authored outside the builder), `VIEW_BUILDER` → `template/view-builder-template` (a page whose layout/fields were assembled visually in the console). Per-object auth (`useAuthValidation`) and authority checks (`useAuthorityValidation`, via `ViewObjectService.validateAuthorization`) gate access to individual pages, mirroring the console's own auth filter.

### Workflows are the request-handling unit for generated pages

Generated pages don't call bespoke controllers — they POST a `RequestMessage` (workflow code + a keyed map of message bodies) to a workflow endpoint, and `WorkflowService.execute` runs it (`POST /workflow` takes JSON, or `multipart/form-data` for uploads — see `WorkflowMultipartMapper` below):
1. Look up the `Workflow` by code, authenticate if `useAuthValidation`, then authorize against `WorkflowAuthority` (a special `VALID_PASS` authority code means "any authenticated user").
2. Load its `WorkflowNode` nodes plus the `WorkflowEdge` rows that connect them, and assemble both into a `WorkflowGraph`. Nodes are identified by `nodeId` (not the DB id, which changes on every save since the console rewrites all nodes); edges are `sourceNodeId` → `targetNodeId` with a `BranchType`: `DEFAULT` for ordinary flow, `CASE` (plus a `branchId`) for one branch of a condition, `ELSE` for its fallback branch. Execution walks the graph from the start node (the one with no incoming edge); a node with no outgoing edge ends the flow. `orderNum` is only the builder's display order and never decides what runs next.
3. Each node names a `FunctionType` (`ENTITY`, `SQL`, `REST_CLIENT`, `MESSAGE_PROCESSOR`, `NOTIFICATION`, `FILE`, `CONDITION`, `ERROR_MESSAGE`) and reads/writes a slot in a shared `Map<String, List<Map<String,Object>>>` message store keyed by `requestMessageId`/`responseMessageId` — this is how steps pass data to each other. `FunctionFactory.instance(FunctionType)` resolves a node to a `NodeExecutor` implementation (`function/executor/*`); each executor's `execute(user, functionName, params)` does the real work and returns a `NodeResult` (success/failure). `CONDITION` is the exception: it produces no data. Its branches are `WorkflowCondition` rows (one per `if` / `else if`, ordered by `orderNum`, each with a `branchId` that ties it to its `CASE` edge). `WorkflowService` evaluates them in order through `ConditionEvaluator` (JS via `executor/script`, with `params` = the node's IN slot), follows the `CASE` edge of the first one that is true, and falls back to the `ELSE` edge when none match — nodes on the branches not taken never run and never appear in the response. `ERROR_MESSAGE` is the other control node: reaching it stops the flow (even if edges continue past it) and returns its `WorkflowErrorResponse` row (`status`/`code`/`message`, plus `contents` = comma-separated message IDs copied from the message store) as the error response; `status` doubles as the HTTP status and falls back to 400 if it isn't a 4xx/5xx.
4. If every step succeeds, the accumulated response slots become the workflow's response body; if some (but not all) steps fail, a partial-failure error is returned with everything gathered so far.

The workflow builder console screen (`templates/console/contents/workflow-builder.html`) is a free-form canvas: nodes are placed at `WorkflowNode.positionX/positionY` (builder-only values, ignored at execution time) and every connection is drawn by dragging a node's output port onto another node, so two branches can converge on one shared node instead of duplicating it. Nodes without a stored position (saved before the canvas existed) are auto-laid-out on load, and a workflow with nodes but no edges is read as an `orderNum` straight line so old definitions migrate on the next save.

File uploads reach a workflow through the multipart variant of `POST /workflow` (`WorkflowController.workflowMultipart` → `WorkflowMultipartMapper`, picked over the JSON mapping by its `consumes` condition): the `message` part carries the usual `RequestMessage` JSON (a form field or a JSON blob part), and every file goes in a part named `files` (any other file part name is a 400). Uploaded files ride on `RequestMessage.Header.files` (`@JsonIgnore`), never in the message body — the body is echoed back by partial-failure responses and `ERROR_MESSAGE` nodes, and a `MultipartFile` in there would break the JSON response. The header is what every `NodeExecutor.execute(user, functionName, header, params)` receives, so `FileExecutor` hands each uploaded file to `FileService` as `FileRequest.multipartFile` while the node's ordinary request message supplies the path values — e.g. `body.uploadParam = [{"boardId":"7"}]` with a handler path of `board/#{boardId}/#{original_filename}`, where `original_filename` is filled from the uploaded file's own name. With files present the node runs once per file, paired with the request message rows in order: no rows → empty params, exactly one row → shared by every file, n rows → the nth file gets the nth row, and any other count fails the node without writing anything. With no files it falls back to the usual one-run-per-row. Client side, `HttpClient.postFiles(url, requestMessage, files, ...)` builds that form. Upload size is capped by `spring.servlet.multipart` in `application.yml` (50MB).

When adding a new kind of workflow step: add a `FunctionType`, an executor implementing `NodeExecutor`, and wire it into `NodeExecutorFactory`. Control-flow nodes like `CONDITION` and `ERROR_MESSAGE` are the exception — they are handled in `WorkflowService`'s traversal, not by an executor.

### Rest API: workflows exposed as REST endpoints

`restapi/` wraps a workflow as a plain REST endpoint (console screen `console/contents/rest-api.html`). A `RestApi` row is `httpMethod` (GET/POST/PUT/DELETE only) + `path` (may contain `{var}`) + `workflowCode`; `RestApiController` catches everything under `/rest/**` (`RestApi.URL_PREFIX`; not `/api/**`, which existing controllers already use) and `RestApiExecuteService` resolves the definition by `PathPattern` match (most specific wins; path matches but method doesn't → 405, nothing matches → 404). `RestApiParameter` rows are the schema — `paramIn` PATH/QUERY/HEADER/BODY, `dataType`, `required`, `defaultValue` — plus where each value lands in the workflow `RequestMessage` body: `messageId` + `mappingKey` (defaults to `name`). `RestApiRequestMapper` validates/converts and builds the message store: PATH/QUERY/HEADER values and a body OBJECT go into one "base row" per message ID, a body ARRAY (or a nested OBJECT/ARRAY field with its own `messageId`) produces rows, and when a message ID has both, base values are copied into every array row. Body fields form a tree via `paramKey`/`parentKey` (like workflow `nodeId`, stable across the delete-and-reinsert save). The response side is configured on the same definition: `responseType` JSON (default) or FILE. For JSON, `RestApi.responseMessageId` picks the one workflow response message whose content replaces `contents` (no message-ID key — callers never see workflow message IDs; blank → whole `contents` as-is), `responseDataType` ARRAY returns all rows / OBJECT the first row or null, and `paramIn=RESPONSE` rows are the row field schema applied by `RestApiResponseMapper` (`mappingKey` = source column, value converted to `dataType`; no fields → rows pass through; requires a `responseMessageId`). A value that can't be converted is a 500 `E-RESTAPI-006`. The envelope (`status`/`code`/`message`/`resultType`) is always kept. For FILE, the first row of `fileMessageId` supplies the bytes (`fileContentKey`: `byte[]`/`Blob`, or a string decoded per `fileContentEncoding` BASE64/TEXT — `MULTIPART` is request-side only and rejected on save), file name and content type, returned as an `attachment`. Response settings only apply to successful workflow runs; failures always return the workflow's JSON error. Request-side schema violations return 400 with the offending location (e.g. `Request Body 'body.goals[1].goalId'`); auth/authority is whatever the wrapped workflow requires. The console screen also has a "테스트 호출" tab (a browser `fetch` to the real `/rest/...` URL, so it runs against the *saved* definition) and an API document view fed by `GET /console/api/rest-api/document` (`RestApiDocumentService`: parameter schemas plus the wrapped workflow's response message IDs and `ERROR_MESSAGE` node errors).

### Function executors and the lower-level `executor/` package

`function/executor/*` are the workflow-facing adapters; they delegate to lower-level, reusable engines in `executor/`:
- `executor/sql` — parameterized SQL execution (`SqlExecutor`, `SqlQuery`) with pluggable parameter binding (`parameterbind/`: index-based vs named-based binding).
- `executor/rest` — outbound HTTP calls to externally-registered REST servers (`RestExecutor`).
- `executor/script` — sandboxed JS execution via GraalVM Polyglot (`ScriptEngine`): params are JSON-marshalled in, the user script is wrapped in an IIFE, run with `allowAllAccess(false)`, and the result is walked back into plain Java `List`/`Map`/primitive values. Used for the `MESSAGE_PROCESSOR` function type's custom transform scripts.
- `executor/notification` — outbound notification senders (SMTP today: `SmtpProvider`, `NotificationSender`), pluggable by `NotificationType`.

Entity CRUD (the `ENTITY` function type) doesn't go through `executor/sql` directly — it goes through `entity/query/EntityQueryGeneratorFactory`, which builds the appropriate `InsertQuery`/`SelectQuery`/`UpdateQuery`/`DeleteQuery` from an `EntityConfig` + `EntityColumn` definitions based on `EntityStatus` (C/R/U/D), driven off the console-defined entity metadata rather than JPA entities.

### Dynamic data sources

Because generated admin pages manage *other* databases and *other* REST servers (not just the app's own H2 store), `datasource/database` and `datasource/restserver` hold connection registries: `DatabaseFactory` builds a `Database` strategy per `DatabaseKind` (MySQL/MSSQL/Oracle/MariaDB — each with its own SQL dialect quirks), and `DataSourceDatabaseRegister`/`DataSourceRestServerRegister` register/validate connections defined through the console (`console/rest/DatabaseRestController`, `RestServerRestController`) so `executor/sql` and `executor/rest` can use them by a lookup key at runtime. `datasource/filestorage` does the same for file storages (`DataSourceFileStorage`: `storageType` + type-specific `options` JSON; only `LOCAL` with `rootPath` today → `executor/file/LocalFileStorage`, which rejects paths escaping the root). The `FILE` workflow node (`file/FileHandler` + `FileService`, console popup `workflow-file.html`) runs one `actionType` READ/UPLOAD/DELETE against storage root + `filePath` (`#{param}` expressions); what it uploads depends on `fileContentEncoding`: `MULTIPART` ignores `fileContentKey` and writes `FileRequest.multipartFile` — the file the request uploaded — through `FileStorage.write(path, MultipartFile, overwrite)`, which streams it to disk (`Files.copy`) instead of buffering the whole file in memory, and fills the `original_filename` param from it so `board/#{boardId}/#{original_filename}` keeps the uploaded name; otherwise the value under `fileContentKey` is used (`byte[]`/`Blob` as-is, a string decoded per BASE64/TEXT). READ returns the bytes under `fileContentKey`. The console execute endpoint `POST /console/api/file/{handlerName}/execute` accepts either JSON (base64/text) or `multipart/form-data` — form fields become params and the first uploaded file becomes `FileRequest.multipartFile`, the same path the workflow takes.

### Security

JWT-based auth, not Spring Security's filter chain — `security/filter/ConsoleSecurityFilter` is a plain `Filter` registered manually via `FilterConfig` (not `SecurityFilterChain`). `AuthService`/`LoginService` validate credentials and issue tokens (`JwtProvider`, `TokenCookie` — access token in an HTTP cookie). Authorization is role/authority-code based (`GrantedAuthority`, `Authority`, `UserGroupAuthority`) and is checked independently at three levels: console access (`ConsoleSecurityFilter`), per-view-object (`ViewObjectService.validateAuthorization`), and per-workflow (`WorkflowService.validateAuthorization`) — all following the same "does the user hold one of the authority codes assigned to this resource" pattern, with a `VALID_PASS` sentinel meaning "any authenticated user, no specific authority needed." Generic low-level security primitives (password hashing, business exception base class) live in the separate `com.prometis.core` package (`core/crypto`, `core/exception`, `core/util`), not `com.prometis.appbuilder.security`.

Workflows have a second, independent gate next to authorities: IP access control (`security/ip`, checked in `WorkflowService.execute` via `IpAccessValidator` right after the authority check). Allowed IPs are kept in groups — an `IpGroup` (unique `groupCode`) holding `IpAddress` rows, each a single IP, a CIDR range, an IPv4 wildcard (`192.168.0.*`) or `*`, with an `enabled` flag (`IpAddressMatcher` does the comparison; host names are never resolved). A workflow points at groups through `WorkflowIpGroup` (`ipGroupCode` + workflow, mirroring `WorkflowAuthority`), saved with the workflow by `WorkflowRestController.save` from the builder's settings panel. **No mapped group means no IP restriction**; once a group is mapped, the caller's IP (`ClientIpResolver`: first `X-Forwarded-For` entry, then the other proxy headers, then `getRemoteAddr`) must match an enabled entry or the run is rejected with 403 `E-WORKFLOW-011` — an empty group therefore blocks everything, and a run with no HTTP request at all (the scheduler) skips the check. Groups and their IPs are managed on the `ip-management` console screen (sidebar Security → IP 관리), which the workflow builder also opens as a modal popup from its IP settings field; deleting a group that a workflow still maps is refused so a restriction can't be dropped silently, and renaming a `groupCode` rewrites the mappings.

Domain access control (`security/domainaccess`, `DomainAccessValidator`, checked right after the IP check) is the third gate and works the same way, minus the grouping: allowed domains hang directly off the workflow as `WorkflowDomain` rows (`domain` + workflow), typed into the builder's settings panel and saved with the workflow, with the same "no rows means no restriction" rule. The caller's domain is the `Referer` host (`Origin` when there is no referer; neither one present is a rejection, so server-to-server callers can't be domain-restricted), compared by `DomainMatcher` case-insensitively and ignoring ports: an exact host, `*` for everything, or a wildcard where a leading `*.example.com` covers sub-domains at any depth — but not `example.com` itself — and a `*` inside one label (`dev-*.example.com`) stays within that label. A mismatch is 403 `E-WORKFLOW-012`. Domain format is validated in `WorkflowRestController.save` before anything is written, so a bad entry can't leave a half-saved workflow.

### Frontend

Server-rendered Thymeleaf + AdminLTE, no separate frontend build/bundler. Shared client-side helpers live in `src/main/resources/static/core/` (`HttpClient.js` for calling workflow endpoints, `Grid.js`/`GridLegacy.js` wrapping ag-Grid for data tables, `Popup.js`, `Util.js`) and are reused across both the console screens and generated `VIEW_BUILDER`/`FILE` pages.
